## 1. What this project is

**Lit Bulb Lab** (brand name) — an accessibility-first tech/finance/photography explainer blog living at **https://abedis.net** (repo name on GitHub: `abedis-lab`; npm package name: `lit-bulb-lab` — three different names for the same thing, be aware when searching).

Tagline: *"Hard things, drawn simple."*

- **Format:** one short, illustrated explainer post per day, published automatically at midnight by a 5-stage AI pipeline (research → write → illustrate → edit → publish) running entirely through the `claude` CLI on this Mac — no external API key, no cloud compute, no CI service. It runs unattended, overnight, on a single developer's laptop/desktop.
- **Categories:** AI, Tech, Trading, Tinkering (photography/gadgets/watches/coffee).
- **Audience** (from `PRODUCT.md`): neurodiverse readers (ADHD, dyslexia), older/non-technical readers, and people who know the topic but want a better explanation than the docs.
- **Distribution:** Instagram carousel (@litbulblab) generated by the same pipeline, but **posted manually** — this is the single biggest unsolved gap in the automation (see §7).
- **Design ethos:** warm paper palette, single `#d6552b` orange accent, Fraunces (display) + Atkinson Hyperlegible (body) fonts, WCAG AA, dark mode, "one idea per screen," never looks AI-generated/generic. Full brand doc: `PRODUCT.md` at repo root — read it, it's short and dense with intent.

As of this writing: **32 posts published** (day 0 through day 31 in the content calendar), the pipeline ran successfully last night (2026-08-14, published "The exposure triangle explained"), and **1 topic is queued** ("Why golden hour light looks different," day 32, status `pending`).

## 4. The nightly publishing pipeline (the core deliverable)

This is the most valuable and most fragile part of the project. Everything below lives under `scripts/pipeline/`.

### 4.1 How it's triggered
- `~/Library/LaunchAgents/net.litbulb.pipeline.nightly.plist` (identical copy checked into the repo at `scripts/pipeline/net.litbulb.pipeline.nightly.plist`) — `launchd` `StartCalendarInterval` at **00:00 (midnight) local time**, runs `/bin/bash scripts/pipeline/run_pipeline.sh`.
- **Rebuild step on a new machine:** `cp scripts/pipeline/net.litbulb.pipeline.nightly.plist ~/Library/LaunchAgents/` then `launchctl load ~/Library/LaunchAgents/net.litbulb.pipeline.nightly.plist`. There's also a `net.litbulb.pipeline.test.plist` for manual/one-off test invocation.
- **launchd gives the job a minimal PATH** (`/usr/bin:/bin:/usr/sbin:/sbin`) — `run_pipeline.sh` explicitly prepends `$HOME/.local/bin:/opt/homebrew/bin:/usr/local/bin` because that's where `claude`, `yq` (brew), and `node` live on this specific Mac. **This will need adjusting on any other machine** — check `which claude yq node` and match the script's PATH export to reality.
- **launchd sets no working directory**, so the script resolves its own repo path via `$(dirname "${BASH_SOURCE[0]}")` and `cd`s there explicitly. This was itself the root cause of a full night's failure on 2026-07-05 (see git history / memory) — don't remove that `cd`.

### 4.2 Orchestrator: `scripts/pipeline/run_pipeline.sh`
Read the whole file — it's ~370 lines and fully commented on *why*, not just *what*. Summary:
- Pulls the next `status: pending` entry from `content-calendar.yaml` (topic/category/slug), or runs a one-off test topic if `TEST_TOPIC` env var is set (test runs never touch git or the calendar).
- Runs 5 stages in order via `claude -p "<rendered prompt>" --model <model> --dangerously-skip-permissions --settings scripts/pipeline/pipeline-settings.json --strict-mcp-config --mcp-config '{"mcpServers":{}}'`.
  - `pipeline-settings.json` = `{"disableAllHooks": true, "includeCoAuthoredBy": false}` — hooks are disabled for unattended runs (so nothing in this user's global hook config, e.g. the "Ponytail" or "RTK" hooks referenced elsewhere in this Mac's Claude config, interferes with pipeline runs).
  - `--strict-mcp-config` with an empty server list means none of the user's personal MCP servers (Gmail, Drive, browser, etc.) load into pipeline sessions — cheaper and quieter.
- **Model assignment** (tuned to stretch a subscription's session budget): `01-researcher` and `05-publisher` run on **haiku** (mechanical/extraction work); `02-writer`, `03-illustrator`, `04-editor` run on **sonnet** (judgment/design — haiku repeatedly stalled on the illustrator stage and once shipped a mislabeled chart).
- **Success is judged only by a `verify_cmd` per stage** checking for expected output files on disk — never by the CLI's exit code or prose output alone (`claude -p` exits 0 on any completed turn regardless of what it actually did).
- **Failure classification** (this is the sophisticated part, don't flatten it back to "just retry"):
  - **Editor content-flag** (core-premise failure, e.g. fabricated citation) → not a same-stage retry. The editor's specific findings are appended to a fresh 01-researcher prompt and the *entire* chain re-runs once. A second block on the same topic → terminal failure, needs human review. (Completed stage checkpoints are deliberately never blind-wiped without the editor's critique attached — a prior incident let a hallucination back in that way.)
  - **Session rate limit** (Claude subscription hit its usage window) → sleep until the stated reset time + 5 min buffer, then resume — capped by a `MORNING_DEADLINE` (default 07:30) after which the night is declared lost. Does not consume a stall retry.
  - **Transport/API error** (`ECONNRESET`, `fetch failed`, etc.) → exponential-ish backoff (120s × attempt number), up to 3 attempts.
  - **Anything else** → exactly one informed retry of the failed stage, with the previous failed attempt's output appended to the retry prompt so the model doesn't repeat the same mistake blind.
- Instagram SVG slides get rasterized to PNG immediately after stage 03 via `scripts/pipeline/svg-to-png.mjs` (Instagram doesn't accept SVG uploads).
- State/checkpoints/logs: `scripts/pipeline/state/` and `scripts/pipeline/logs/` (both gitignored — **this local run history does not exist anywhere except this Mac**; if you want to preserve the pipeline's operational history before this machine goes away, copy these two directories out separately, they are not in git).

### 4.3 Stage prompts: `scripts/pipeline/stages/*.md`
Five files, each read directly — they're short, precise, and worth reading verbatim rather than summarized:
- `_unattended.md` — prepended to every stage: hard rule against asking questions (nobody's there to answer), success defined only by output files existing, write a `-blocked.md` file if genuinely stuck.
- `01-researcher.md` — gathers 3-5 sourced facts, one analogy, one counterintuitive hook, 2-3 concrete examples, one funny angle. **Every claim needs a source URL on the same bullet — no source, doesn't go in the file.** This discipline exists because an uncited fake version number from a junk source already cost the blog a post once.
- `02-writer.md` — writes the full MDX post from the research file only (forbidden from adding any fact not in research). Picks the strongest of 3 candidate hooks, checks existing post titles to avoid reusing a title formula (two posts already used "X vs Y: You're Not Actually Choosing" — a third is explicitly banned in-prompt). Leaves `{/* IMAGE: ... */}` MDX-comment placeholders (HTML `<!-- -->` comments **break the MDX build** — this is called out explicitly because it happened before).
- `03-illustrator.md` — fills image placeholders. **Tries `GEMINI_API_KEY` first if set, falls back to hand-authored SVG if not set or on any API error.** This Mac currently has no evidence `GEMINI_API_KEY` is set anywhere findable — the pipeline has been running on the SVG fallback path this whole time (32/32 posts use `.svg` images, not raster). This is a live "pending decision" per the project's own memory (keep or delete the unused Gemini path). Also generates 5 Instagram slides (1080×1080 SVG) to `~/Desktop/litbulb-instagram/<date>-<slug>/`.
- `04-editor.md` — last line of defense. Fixes fixable issues directly (softens overclaims, fixes image paths) rather than just reporting them. Only *blocks* for core-premise failures (wrong central claim, topic misunderstood).
- `05-publisher.md` — **states the live site is "Cloudflare Pages, connected to `main`, auto-deploys on push"** — this is stale/imprecise per the project's own more recent operational memory (see §5, it's actually a Worker now, not classic Pages), but functionally the auto-deploy-on-push-to-main behavior is what matters and that part is still true regardless of the Pages/Workers naming. Runs `npm run build` as a precondition check before ever committing. Commits with message `Add post: <title>`, pushes, flips the calendar entry to `status: done`, pushes that too, writes a `-SUCCESS.md` state file.

### 4.4 Content calendar: `content-calendar.yaml`
Flat YAML list, one entry per day: `day`, `category`, `topic`, `slug`, `status` (`pending`/`done`). The pipeline always pulls the **first** `pending` entry, so entries should stay in the order you want them published. **This file needs topics added periodically** — the owner has been adding batches of 8-10 topics every couple of weeks by hand (see git log: `content-calendar: add N new topics (days X-Y)`). At day 32/pending, there is roughly **one day of runway left** before the pipeline has nothing to publish and exits as a no-op. **If resuming this project, refill the calendar before restarting the launchd job**, or the pipeline will just log "Nothing to publish" every night.

Subscription session limits can still kill overnight runs; the sleep-until-reset logic mitigates but doesn't eliminate this. **Decide, on resume, whether to switch to a metered API key** for reliability, weighed against cost.

3. **Gemini image path is dead code that's never exercised** — decide whether to wire up `GEMINI_API_KEY` for real image generation or delete the branch in `03-illustrator.md`/rip it out.

## 5. Deployment infrastructure (Cloudflare)

### 5.1 What's actually configured
The site deploys as a **Cloudflare Worker**, not classic Cloudflare Pages, even though it's colloquially (and in the `05-publisher.md` prompt) still called "Pages." Astro's `@astrojs/cloudflare` adapter and `wrangler` are **not committed to `main`** — Cloudflare's build pipeline runs `astro add cloudflare` non-interactively as part of every single build, installing the adapter fresh each time. This means:
- `wrangler.jsonc`/`wrangler.toml` will **never** be found by grepping the checked-out `main` branch.
- **Recovery path if you need the actual worker config:** a bot commit exists on the never-merged remote branch `origin/cloudflare/workers-autoconfig` (commit `3c80b07`, made 2026-07-03 by the `cloudflare-workers-and-pages[bot]` GitHub App at the moment this project was first connected to Cloudflare). That commit's `wrangler.jsonc` is:
  ```jsonc
  {
    "$schema": "./node_modules/wrangler/config-schema.json",
    "compatibility_date": "2026-07-03",
    "compatibility_flags": ["global_fetch_strictly_public"],
    "name": "lit-bulb-lab",
    "main": "@astrojs/cloudflare/entrypoints/server",
    "assets": { "directory": "./dist", "binding": "ASSETS" },
    "observability": { "enabled": true }
  }
  ```
  along with `astro.config.mjs` gaining `adapter: cloudflare()` and `package.json` gaining a `deploy`/`preview`/`generate-types` scripts + `wrangler`/`@astrojs/cloudflare` deps. **This branch was deliberately never merged** — the team relies on Cloudflare auto-configuring this at build time instead. Treat this recovered config as a strong reference for what the dashboard's build settings produce, not as something to blindly merge.
- **Naming discrepancy to resolve on resume:** earlier operational notes from this project referred to the deployed Worker as `litbulbnet`, but the bot-generated config above says `"name": "lit-bulb-lab"`. **Log into the Cloudflare dashboard and check the actual Worker name before assuming either is current** — it may have been renamed at some point, or one of these records is simply wrong.
- Build command: `npm run build` (which runs `prebuild` → `og-gen.mjs` → `astro build`). Output directory: `./dist`.
- **No `.github/workflows` exist** — there is no GitHub Actions CI. Cloudflare's own git integration watches `main` and deploys on every push, triggered both by manual `git push` and by the pipeline's own `05-publisher` stage.

### 5.2 The `_redirects` gotcha (already hit once, will hit again if repeated)
Cloudflare Workers' `_redirects` file (would live at `public/_redirects` if it existed) only accepts **relative, same-host** rules. A rule crossing hosts (e.g. `www.abedis.net` → `abedis.net`) passes the Astro build cleanly but makes `wrangler deploy` **hard-fail at the very last step**, with the failure surfacing nowhere visible except the Cloudflare dashboard's deployment log — not in the git push, not in `05-publisher`'s build check (which only checks `astro build`, not the actual Cloudflare deploy step). This already broke deploys once (git history: `Redirect www.abedis.net to apex domain` immediately reverted by `Revert www redirect via _redirects file`). **Never use `public/_redirects` for a cross-host redirect.**

**Correct fix for cross-host redirects** (e.g. www → apex, already implemented this way): Cloudflare dashboard → zone `abedis.net` → Rules → **Redirect Rules** (zone-level, evaluated before the Worker even runs). There's a built-in "Redirect from WWW to root" template. The dashboard will show a "This rule may not apply to your traffic" DNS warning — **this is a false positive** for this setup (both `www.abedis.net` and apex `abedis.net` are CNAMEs to `abedis-lab.pages.dev`, both orange-cloud Proxied) — click "Ignore and deploy rule anyway," do not let it talk you into creating a new DNS record.

### 5.3 DNS records for `abedis.net` (as last verified, may have drifted)
- `abedis.net` (apex) and `www.abedis.net` — both CNAME to `abedis-lab.pages.dev`, both Cloudflare-proxied (orange cloud).
- `ipo.abedis.net` and `garuda.abedis.net` — **A records to `13.205.6.100`, a separate AWS box running Caddy, completely unrelated to this project.** Don't assume every `*.abedis.net` subdomain is part of Lit Bulb Lab.

- **Domain registrar for `abedis.net` is not documented anywhere in this repo or memory** — the new owner/agent will need this from the project owner directly to make any registrar-level changes (nameservers, etc.), though DNS records themselves are managed in Cloudflare, not the registrar, as long as Cloudflare stays the nameserver.
